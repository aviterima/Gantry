# v0.4 testing release — scope and acceptance

The owner requested the full build ready for testing. This release provides the
end-to-end operational workflow in a local sandbox and as a buildable Cloudflare
Worker. It does not claim production readiness or live integration acceptance.

| Target | Available for testing | Still required for production acceptance |
|---|---|---|
| Selection/G0 | Intake, scorecard, evidence, research-provider boundary, memo, access keys, locked numeric plans | Ten real candidates; live research quality/cost; concurrent selection storage |
| Launch preparation | Approved-candidate snapshot, readiness evidence, offer/playbook editor, authenticated landing preview | Public domains, real booking/payment and delivery service |
| Channel integration | Strict CSV import, source/angle attribution, shared CRM stage taxonomy, reservations and global suppression | Verified Neubloc/Vox/Forum API contracts and adapters, webhooks, warmup and real health checks |
| Signal engine | Idempotent events, order identity, refunds, stage-appropriate metrics, spend/deadlines, channel costs and full trace | External event authenticity, provider reconciliation, normalized production-scale event tables |
| Gate management | Human pass/kill/extend, one shorter extension, immutable original plan, G2 concentration and budget authorization | Operational concentration response and real results |
| Wind-down | Customer/export/refund/opt-out/domain tasks; retained cluster-tagged learnings | Actual notices, refunds, domain retention and independent completion checks |
| Portfolio | Concurrent tournaments, reviewer capacity, mix counts, dated review queue, calendar export, rescheduling | Live cluster asset health, measured capacity policy, background notifications |
| Promotion | Operator/concentration requirement, evidenced G4 checklist, signed promotion | Entity, equity and contractual execution |
| Handoff | ZIP with signed snapshots, signals, audit, staged CRM, playbook, debt, specs and runnable landing scaffold | Actual venture product, verified Forum export, one-day engineer acceptance |
| Candidate generation | Human intake and optional configured research | Continuous listening and automatic discovery remain unimplemented |

## Test evidence

Release suite: 60 Python/API tests, 10 operations-kernel tests and 2 Chromium
end-to-end tests (72 automated tests in total).

- Python/Worker HTTP tests exercise the full service-first lifecycle, stale revisions,
  capacity, suppression, atomic ingestion, deduplication, extension limits, kill and
  wind-down, promotion and handoff ZIP contents.
- Kernel tests exercise the self-serve week-2 return window, budget/deadline queue,
  attribution, plan constraints, order validation and immutable snapshots.
- Chromium exercises manual selection and the complete operations workflow through
  actual UI controls, including landing inquiry, import, promotion and ZIP download.
- Desktop and mobile screenshots were inspected; no page errors or page-wide mobile
  overflow were detected in the tested flows.
- The real local launcher is started and restarted under test. Credentials and the
  isolated demo data survive restart. Generated handoff smoke tests are executed.
- Formatting, lint, Python type checks, schema generation and Worker dry build are
  release gates. Remote CI validates the committed release.

The Windows `.cmd` launcher is supplied, but this execution environment is Linux;
its underlying Python startup path is tested, not Windows desktop behavior.
Worker contract tests execute the actual module with a deterministic storage adapter;
no production Cloudflare migration or cross-region acceptance run was performed.

## Review points

The >=35 G0 approval floor remains proposed for owner acceptance. Imported money
uses integer cents; a refund event represents reversal of a complete order. Arbitrary
partial refund accounting is outside this testing model. Numeric plans cannot be
added to old signed G0 decisions: use a newly reviewed candidate instead. Sandbox
fixtures are explicitly synthetic and are created only in an isolated testing folder.
